# Инструкции агентам команды «ИИксперты»

## Цель и источники

Создать прототип «Умная парковка» для ОС Аврора за оставшееся время хакатона. Требования и проверяемые результаты описаны в `docs/REQUIREMENTS.md`. Технические решения проверять по официальному порталу https://developer.auroraos.ru и реальному шаблону установленного SDK. Не придумывать API Авроры, команды SDK, версии библиотек и результаты тестов.

Комплект команды: Aurora SDK **BT 5.2.1.200**, Docker Desktop, соответствующий эмулятор. Использовать Qt из SDK. Не переносить API Qt 6 в проект без проверки. Для нового проекта выбрать qmake. На BT основной инструмент командной строки — `apptool`; синтаксис смотреть в справке установленной версии.

## Архитектура и код

Слои и интерфейсы описаны в `docs/ARCHITECTURE.md` и `docs/CONTRACTS.md`. C++ отвечает за валидацию, БД и бизнес-правила. QML отвечает за отображение и действия пользователя. Все обращения к общей SQLite connection выполняются в одном потоке. Схему меняет только интегратор, каждый модуль записывает только свои таблицы.

Классы и QML-компоненты — `PascalCase`, методы и свойства — `camelCase`, поля SQLite и JSON — по контракту. Использовать форматирование существующего шаблона, стандарт C++, поддержанный SDK, и параметризованные SQL-запросы. Денежные суммы хранить в целых копейках, время — UTC. Пользовательские тексты, issues и документация — на русском.

## Ветки, отчётность и проверка

Ветка: `feat/<номер-issue>-<краткое-имя>` либо `fix/<номер-issue>-<краткое-имя>`. PR направлять в `main`, в описание включать `Closes #N`, список изменённых интерфейсов и результат проверки.

Через 10 минут после начала задачи оставь комментарий в issue: что проверено, следующий шаг, препятствие. О блокирующей ошибке сообщай сразу, приложив короткий лог без секретов. Чужую ветку не переписывай. Force-push в `main`, удаление репозиториев и чужих веток запрещены без явного согласия Григория.

До слияния PR требуется реальная сборка в согласованном SDK, проверка относящихся к задаче бизнес-правил и запуск соответствующего сценария в эмуляторе. Если SDK ещё не работает, открыть draft PR и прямо написать «сборка не проверена». При отсутствии runtime допустимы проверки JSON/SQLite, но они не заменяют сборку приложения. После каждого этапа интегратор проверяет полный сценарий в эмуляторе.

Не менять общую сборку просто ради подключения своих новых файлов: приложить к PR точный список нужных изменений для интегратора либо получить согласование. Общие файлы меняет один исполнитель за раз.

## Безопасность и сдача

Не коммитить токены, пароли, ключи подписи, `.env`, пользовательские БД, IDE-настройки и установщики. Не копировать чужой токен из официального примера MFW. У всех заимствованных файлов сохранять лицензию и авторство. Собственный код — MIT.

Демо-вход и симуляцию оплаты обозначать в интерфейсе. Не собирать банковские реквизиты и реальные одноразовые коды. Результаты ИИ проверять, фактически использованные инструменты и этапы заносить в `BASE_INFO.md`.

Не объявлять задачу, функцию или этап готовыми без результата проверки. Декоративные улучшения и новые функции прекращаются за 90 минут до дедлайна. Приоритет — рабочие этапы 1–3, затем история, темы и уведомления.
