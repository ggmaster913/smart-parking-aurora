# Архитектура v0.1

Решения приняты координатором в рамках переданной Григорием автономии. Номер версии SDK подтверждён официальной страницей загрузок; сборка на компьютерах команды пока не подтверждена.

## Подход

Выбрано нативное приложение из шаблона SDK: C++ для данных и бизнес-правил, QML/Silica для интерфейса, SQLite для состояния, локальный JSON для парковок. Вход и оплата явно демонстрационные. Это позволяет проверить основной сценарий без отдельного сервера и зависимости от реальных платёжных/парковочных сервисов.

Альтернатива с небольшим HTTP-сервером добавляет настройку сети и развёртывание без обязательной функции. Реальный API может дать бонус, но несёт риск доступа и нестабильности. Оба варианта отложены до стабильного ядра и подготовленной сдачи.

## Структура

```text
src/main.cpp                создание сервисов и привязка к QML
src/core/                   DatabaseManager, SessionContext, миграции, общие типы
src/account/                AccountService: демо-вход, профиль, автомобили
src/parking/                ParkingService: зоны, места, расстояния
src/booking/                BookingService: стоимость, талон, активная сессия
qml/App.qml                 корневой интерфейс и навигация
qml/account/                вход, профиль, автомобили
qml/parking/                карта, список, карточка зоны, выбор места
qml/booking/                подтверждение, талон, активная парковка, история
qml/cover/                  обложка приложения из шаблона SDK
data/parking-zones.json     вымышленные зоны и начальная занятость
migrations/001_initial.sql  единственная начальная схема
tests/account/              проверки данных профиля и автомобилей
tests/parking/              проверки каталога, координат и сортировки
tests/booking/              расчёт и переходы состояния парковки
third_party/mfw/            только необходимые компоненты MFW с лицензиями
docs/                       контракты, запуск, демо и сдача
rpm/                        упаковка SDK
```

Точные имена `.pro`, `.desktop` и корневого QML-файла фиксирует bootstrap из реального шаблона. Если шаблон создаёт другое имя корневого QML, интегратор обновляет документацию и единственный маршрут подключения, не создаёт второй параллельный корень.

## Общие границы

`DatabaseManager` открывает БД в каталоге данных приложения, включает внешние ключи, применяет миграции транзакционно и отдаёт connection сервисам. БД и сервисы используются в одном главном потоке. Миграции и схема принадлежат интегратору. Модули не меняют таблицы друг друга.

`SessionContext` хранит текущий `userId`, доступный QML только для чтения. AccountService меняет контекст после входа/выхода. ParkingService работает с каталогом, BookingService проверяет пользователя и автомобиль по БД. Интегратор связывает изменение пользователя с обновлением сервисов, а успешную бронь/продление — с обновлением каталога.

Сервисы регистрируются в QML как `accountService`, `parkingService`, `bookingService`. Общие контракты находятся в `docs/CONTRACTS.md`. Пока заглушки не реализованы в каркасе, задачи ведутся как draft и не заявляются собранными.

Навигация: вход; профиль/автомобиль; карта/список; карточка зоны; выбор места; подтверждение симулированной оплаты; талон/активная сессия. Илья подаёт в навигацию идентификаторы зоны и места, Альберт получает их через свойства страницы. Страницы не загружают чужие исходные файлы и не меняют чужие сервисы.

## Карта и геопозиция

Илья берёт подключение MFW из официального **MapTemplate** и сначала проверяет библиотеку на выбранном SDK. Полный пример MfwMap с маршрутизацией и геокодингом не переносим целиком. Токен из демонстрационного исходника не используем. Источник подложки выбираем с разрешённым использованием и сохраняем требуемую атрибуцию. Локальный источник MFW проверяем отдельно, прежде чем обещать офлайн-карту.

Qt Positioning получает реальные координаты. При запрете/ошибке GPS показываем понятное состояние и кнопку «Использовать демо-местоположение». Демокоординаты Москвы помечаются в интерфейсе и не выдаются за местоположение устройства. Список зон и сохранённые данные работают без подложки. Такой резервный режим не закрывает требование интерактивной карты этапа 2.

## Сборка и интеграция

Первый рубеж — настоящий проект из SDK, RPM и запуск в эмуляторе. Матвей выполняет bootstrap на Windows, Григорий ревьюит и принимает владение общими файлами. Остальные проверяют SDK параллельно и готовят свои модули по контрактам. При первой готовой машине выбираем её основной сборочной, вторую — резервной. На Mac Григория 8 ГБ ОЗУ, поэтому его установка не должна задерживать сборку всей команды.

В `main` вливаем прикладной код после проверки в SDK и эмуляторе. Новые файлы модулей перечисляются в PR, общую сборку меняет один согласованный исполнитель. GitHub Actions без SDK может проверять данные и документацию, но зелёный такой job не доказывает работоспособность приложения.
