# Инструкции агентам команды «ИИксперты»

## Цель и источники

Создать прототип «Умная парковка» для ОС Аврора за оставшееся время хакатона. Требования и проверяемые результаты описаны в `docs/REQUIREMENTS.md`. Технические решения проверять по официальному порталу https://developer.auroraos.ru и реальному шаблону установленного SDK. Не придумывать API Авроры, команды SDK, версии библиотек и результаты тестов.

Комплект команды: Aurora SDK **BT 5.2.1.200**, Docker Desktop, соответствующий эмулятор. Использовать Qt из SDK. Не переносить API Qt 6 в проект без проверки. Для нового проекта выбрать qmake. На BT основной инструмент командной строки — `apptool`; синтаксис смотреть в справке установленной версии.

## Минимальное участие человека

Участнику достаточно первоначального промпта и команды «проверь обновления на гитхаб» для возобновления. Агент сам выясняет состояние среды, настраивает разрешённые зависимости, выполняет команды, читает ТЗ, пишет код, проверяет, коммитит и отправляет свою ветку/PR. Не перекладывать на человека доступные агенту команды, сбор логов, отчёты, контроль времени и передачу технических сообщений.

Блокировки и вопросы контракта направлять координатору `ggmaster913` прямо в GitHub, продолжая независимую работу. После результата проверять дальнейшие указания/назначения и продолжать доступную задачу без просьбы «продолжать?». В границах issue выбирать обычные технические решения самостоятельно.

Человека привлекать только для действительно необходимого входа/MFA, недоступного системного действия/пароля, несоответствия аккаунта, доступа или решения за пределами разрешений. Сначала использовать доступные инструменты и контекст. Нужные действия объединять в одно короткое сообщение: что сделать, почему агент не может сам, что он продолжит затем. Уже данное разрешение повторно не запрашивать. Перезагрузку компьютера согласовать после сохранения работы.

При завершении сессии сохранять контекст; не обещать неподдерживаемое фоновое наблюдение. Для возобновления достаточно одной команды проверки GitHub. Эти правила учитывать во всех новых ТЗ и промптах команды, сохраняя границы модулей и проверку результатов.

## Получение заданий и команда обновления

Полный единый стартовый промпт: `docs/SETUP_PROMPT.md`. Участника определять по `gh api user --jq '.login'`: `playerr456` — Матвей, `SigmaCoder234` — Илья, `Albe345` — Альберт. Если аккаунт один, различать исполнителей по меткам executor:claude и executor:codex: Claude не берёт задачи Codex, Codex не реализует задачи Claude без явного перераспределения.

По команде «проверь обновления на гитхаб» выполнить реальные проверки: аккаунт/remote/ветка/рабочие файлы, `git fetch origin`, открытые issues с `--assignee "@me"`, их текст и комментарии, собственные PR с ревью и комментариями к строкам, изменения инструкций и контрактов в `origin/main`. Ошибка API не означает отсутствие обновлений. Чужой draft PR не заменяет принятую версию main.

Приоритет: последнее явное указание координатора `ggmaster913`, затем замечания к своему открытому PR, затем начатая задача, затем назначенные доступные `P0`, более ранний этап и меньший номер. Не брать чужие задачи. Если работы нет/зависимость блокирует всё, сообщить в #2. Прочие участники не меняют чужой контракт без согласования координатором.

Перед началом оставить в issue номер, ветку, допустимые каталоги и первый проверяемый результат. После проверки обновлений продолжать актуальную порученную работу без отдельного согласия; при просьбе «только посмотреть» выполнить только чтение. Не создавать бесконечный фоновый опрос.

Вести игнорируемую локальную заметку `.agent-local/<логин>.md` с текущим issue, веткой, прочитанным SHA main, последними указаниями, проверками и блокером. Значимые результаты публиковать в issue. Не хранить там секреты.

## Архитектура и код

Слои и интерфейсы описаны в `docs/ARCHITECTURE.md` и `docs/CONTRACTS.md`. C++ отвечает за валидацию, БД и бизнес-правила. QML отвечает за отображение и действия пользователя. Все обращения к общей SQLite connection выполняются в одном потоке. Схему меняет только интегратор, каждый модуль записывает только свои таблицы.

Классы и QML-компоненты — `PascalCase`, методы и свойства — `camelCase`, поля SQLite и JSON — по контракту. Использовать форматирование существующего шаблона, стандарт C++, поддержанный SDK, и параметризованные SQL-запросы. Денежные суммы хранить в целых копейках, время — UTC. Пользовательские тексты, issues и документация — на русском.

## Ветки, отчётность и проверка

Ветка: `feat/<номер-issue>-<краткое-имя>` либо `fix/<номер-issue>-<краткое-имя>`. PR направлять в `main`, в описание включать `Closes #N`, список изменённых интерфейсов и результат проверки.

Если реализована лишь часть issue, писать «Часть #N» без автоматического закрытия. Задачу закрывает координатор после приёмки. Прямые push в main и слияния PR участниками запрещены; инструкции агентам, контракты и общие файлы меняет координатор. Новые функции, зависимости и изменение стека за пределами issue требуют согласования.

Через 10 минут после начала задачи оставь комментарий в issue: что проверено, следующий шаг, препятствие. О блокирующей ошибке сообщай сразу, приложив короткий лог без секретов. Чужую ветку не переписывай. Force-push в `main`, удаление репозиториев и чужих веток запрещены без явного согласия Григория.

До слияния PR требуется реальная сборка в согласованном SDK, проверка относящихся к задаче бизнес-правил и запуск соответствующего сценария в эмуляторе. Если SDK ещё не работает, открыть draft PR и прямо написать «сборка не проверена». При отсутствии runtime допустимы проверки JSON/SQLite, но они не заменяют сборку приложения. После каждого этапа интегратор проверяет полный сценарий в эмуляторе.

Не менять общую сборку просто ради подключения своих новых файлов: приложить к PR точный список нужных изменений для интегратора либо получить согласование. Общие файлы меняет один исполнитель за раз.

## Безопасность и сдача

Не коммитить токены, пароли, ключи подписи, `.env`, пользовательские БД, IDE-настройки и установщики. Не копировать чужой токен из официального примера MFW. У всех заимствованных файлов сохранять лицензию и авторство. Собственный код — MIT.

Демо-вход и симуляцию оплаты обозначать в интерфейсе. Не собирать банковские реквизиты и реальные одноразовые коды. Результаты ИИ проверять, фактически использованные инструменты и этапы заносить в `BASE_INFO.md`.

Не объявлять задачу, функцию или этап готовыми без результата проверки. Декоративные улучшения и новые функции прекращаются за 90 минут до дедлайна. Приоритет — рабочие этапы 1–3, затем история, темы и уведомления.
